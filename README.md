# MemoryPool：C++17 小对象内存池

基于 **KamaMemoryPool** 学习改写的小对象内存池，使用大小分档、块内切槽、中心空闲链和线程本地缓存管理内存。主要调整包括并发空闲链处理、批量补充与归还，以及正确性测试和基准计时方法。

## 功能概览

- **大小分档**：8～512B，每 8B 一档，共 64 档；请求向上取整，超过 512B 使用系统 `operator new/delete`。
- **块内切槽**：中心池按 4KB 申请内存，优先复用已归还的槽，块内空间不足时再申请新块。
- **线程缓存**：本地链为空时批量补充 64 个槽，缓存达到 128 个时归还一半到中心池。
- **对象接口**：`newElement<T>` / `deleteElement<T>` 封装 placement new、参数转发与析构。
- **测试与构建**：CMake 静态库、独立正确性测试、分配/释放微基准。

## 分配与释放路径

```text
HashBucket::useMemory(size)
  ├── size == 0       → nullptr
  ├── size > 512      → operator new
  └── 按大小选择档位
         ├── 本线程缓存有槽 → 从本地链摘取
         └── 本线程缓存为空
                → 中心池加锁，批量取槽
                → 空闲链不足时，从 4KB 块中切槽

HashBucket::freeMemory(ptr, size)
  ├── ptr == nullptr  → 忽略
  ├── size > 512      → operator delete
  └── 挂回本线程对应档位的缓存
         └── 达到阈值 → 切下一批，归还中心池
```

本地缓存命中时不进入中心锁。批量补充和归还访问中心池，由互斥锁保护共享空闲链及块内分配位置。

## 实现取舍

| 实现 | 作用 | 代价 |
|---|---|---|
| 固定大小分档 | 简化定位与空闲槽复用 | 请求向上取整，存在内部碎片 |
| 4KB 块内切槽 | 将多次小分配合并为较少的系统分配 | 部分块内空间无法利用，块不做运行时回收 |
| 中心池互斥保护 | 串行修改共享链与块内位置 | 补充、归还和扩块时可能竞争 |
| 线程本地缓存 | 减少逐次分配访问中心锁 | 保留额外空闲槽，线程退出时尚未归还缓存 |

原版本使用原子空闲栈，曾在两线程分配、写满和释放的测试中崩溃，故障发生在读取空闲节点的 `next` 时。该结构除了 ABA 风险，还涉及节点出栈后用户覆盖槽内数据、其他线程仍访问该节点元数据的问题。当前实现使用中心锁和线程本地链管理槽的交接。

## 构建与使用

以下命令在 Linux / GCC 环境下运行，需要 C++17、CMake 3.16+ 和 pthread。

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

CMake 提供 `memorypool` 静态库、`correctness_test` 正确性测试和 `MemoryPoolProject` 微基准程序。

### 接口示例

```cpp
#include "MemoryPool.h"

struct Item
{
    explicit Item(int v) : value(v) {}
    int value;
};

int main()
{
    // 在启动工作线程之前初始化一次。
    HashBucket::initMemoryPool();

    Item* item = newElement<Item>(42);
    deleteElement(item);

    void* bytes = HashBucket::useMemory(20); // 使用 24B 档位
    HashBucket::freeMemory(bytes, 20);       // 归还时使用原请求大小
}
```

## 正确性测试

`test/correctness.cpp` 包含 5 组检查，注册为 1 个 CTest 目标：

| 场景 | 实际检查 |
|---|---|
| 全部 64 个大小档位 | 每档同时分配 600 个槽，检查地址唯一、整槽可写及写入后内容 |
| 空闲槽复用 | 归还一个槽后再次分配，检查地址复用 |
| 大小与空指针边界 | 0B、超过 512B、非 8B 倍数、释放空指针 |
| 对象辅助接口 | 构造参数传递、对象内容、析构计数 |
| 并发分配与归还 | 8 线程各执行 20,000 次 64B 分配、写满与归还，检查分配非空并完成循环 |

并发测试尚未维护跨线程在用地址集合，也未覆盖跨线程释放、线程退出归还、构造抛异常和高对齐类型。

## 微基准

```bash
./build/MemoryPoolProject
```

当前基准对比四种请求大小（4/20/40/80B），分别运行 1 线程和 8 线程；工作负载为申请后立即释放。使用 `steady_clock` 按线程计时，join 后汇总，避免共享计时变量的数据竞争。

输出中的“总耗时”是各工作线程耗时之和；除以总操作数得到工作线程的平均每次耗时，不能直接作为并发吞吐或端到端延迟。

系统分配侧使用不内联、带编译屏障的封装，避免分配/释放被优化器消除；两侧封装并不完全对称。该负载不足以支持通用性能倍数比较。进一步比较需要统一防优化方式，并增加批量持有、跨线程释放和不同生命周期的负载。

## 当前边界

- **初始化约定**：使用前、创建工作线程前调用一次 `initMemoryPool()`，不支持运行中重新配置。
- **对齐范围**：池内槽仅保证 8B 对齐，不支持将 `newElement<T>` 作为高对齐类型的通用分配接口。
- **释放契约**：归还时必须提供匹配的请求大小；不检测错误指针、错误大小或重复释放。
- **线程退出缓存**：本地剩余槽不会自动归还中心池；对应块保留到中心池析构，不适合大量短生命周期线程的场景。
- **内存回收**：没有空块回收或向操作系统归还空闲块的机制。
- **异常路径**：对象构造抛异常时尚未自动归还已取得的存储，批量分配的异常回收也待完善。
