# MemoryPool

一个按大小分档的定长内存池：8B–512B 每 8 字节一档，共 64 个池。
项目目标不是"比 malloc 快"这么笼统，而是**把一次小对象分配压到几条指针操作**，并保证并发正确。

## 构建与测试

```bash
cmake -S . -B build && cmake --build build -j
./build/correctness_test        # 正确性：可写 / 不重叠 / 可复用 / 并发不重复分配
./build/MemoryPoolProject       # 性能对比：new/delete vs 内存池
ctest --test-dir build          # 与 correctness_test 等价
```

## 设计

### 中心池：整块申请，块内切槽

每个 `MemoryPool` 维护若干 4KB 块，块头 8 字节存下一块的地址，槽区从块头之后按槽大小对齐开始。
分配优先复用空闲链，没有再切新槽；块用完再向系统要一块。析构时按块链整块释放。

### 线程缓存：分配不进锁

每个线程每种档位一份本地空闲链：

```text
分配：本地链表有货 → 直接摘一个（无锁）
      没货 → 一次向中心池要 64 个，锁只在这一步
释放：挂到本地链；攒到 128 个就还一半回中心池
```

这一步是必需的，不是优化。第一版只用了中心锁，实测比 glibc 的 `malloc` 慢 40 倍：

| 实现 | 8 线程分配+释放 |
|---|---:|
| 单锁中心池 | 438 ns/次 |
| 加线程缓存 | 3.7 ns/次 |
| `new`/`delete`（glibc tcache） | 10.8 ns/次 |

### 为什么不用无锁空闲栈

原始版本的 `popFreeList` 是一个 Treiber 栈。它在并发下会 **ABA**：指针值没变、内容变了，CAS 看不出异常，结果同一个槽发给两个线程 —— 实测 2 个线程就 SEGV，崩在 `oldHead->next.load()`，故障地址是被 `memset` 覆盖过的图案。

指针里加版本号只能缓解，不能消除。这里直接换成互斥锁，把临界区压到几次指针操作；配合线程缓存后，锁竞争只发生在批量补充时。

## 实测

WSL2 / g++ 13.3 / x86-64 / Release。每次都是"申请 → 立刻释放"，四种大小（4/20/40/80B）各一次算一轮。

| 线程 | new/delete | 内存池 | 倍数 |
|---:|---:|---:|---:|
| 1 | 8.4 ns | 2.8 ns | 3.0× |
| 8 | 10.8 ns | 3.7 ns | 2.9× |

两点说明：

- 基准里 `new`/`delete` 用不内联、带编译屏障的薄封装包住，否则 `-O2` 会把整对分配释放删掉，量到 0.0 ns。
- glibc 自己也有一层 per-thread cache，所以差距不是数量级的；这个池赢在**没有每块的元数据头和 size 计算**，输在固定 4KB 块和 64 档的粒度。

## 已知限制

1. **线程退出不归还缓存**：线程缓存里的槽在这个线程结束后不会再回到中心池，只有进程退出时随块释放。要修需要给 `thread_local` 加析构归还。
2. **只有 8B–512B**：更大的请求直接走 `operator new`。
3. **块固定 4KB**：不按槽大小调整，512B 档一块只有 7 个槽。
4. **无对齐保证**：只能保证 8 字节对齐，`alignas(32)` 之类的类型不适用。
5. **`freeMemory` 依赖调用方给对 size**：传错大小会进错池，行为未定义。`deleteElement<T>` 用 `sizeof(T)` 自动传，正常用法不会错。
